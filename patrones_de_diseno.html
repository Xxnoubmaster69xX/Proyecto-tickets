Singleton Creacional

Garantiza que una clase tenga una única instancia en memoria durante la ejecución del programa y proporciona un punto de acceso global a ella.

¿Dónde se implementa?

1. Conexión de base de datos: database/connection.py
Asegura que SQLite tenga una sola conexión abierta desde la UI para evitar problemas de concurrencia y bloqueos.

2. Comunicación interna: patterns/event_bus.py
Asegura que todas las vistas y controladores publiquen y escuchen eventos en el mismo canal.

3. Estado del usuario: utils/session_manager.py
Almacena los datos de la sesión del administrador activo globalmente.

¿Por qué es una buena opción aquí?

  • Evita fugas de memoria y bloqueos de archivos: Especialmente importante en SQLite, que bloquea el archivo de la base de datos si múltiples conexiones intentan escribir simultáneamente.
  • Acceso unificado: Permite consultar el usuario autenticado desde cualquier vista de PyQt6 sin necesidad de pasar variables complejas entre widgets.
# database/connection.py
class DatabaseConnection:
    _instance = None
    _lock = threading.Lock()

    def __new__(cls):
        if cls._instance is None:
            with cls._lock: # Doble validación con Lock
                if cls._instance is None:
                    cls._instance = super().__new__(cls)
                    cls._instance._initialized = False
        return cls._instance

Observer / Publisher-Subscriber Comportamiento

Establece una relación de uno a muchos entre objetos, de forma que cuando un objeto cambia de estado (publica un evento), todos sus dependientes son notificados automáticamente.

¿Dónde se implementa?

Clase EventBus en patterns/event_bus.py.

Cuando el controlador realiza una acción, en lugar de interactuar directamente con la UI, publica un evento en el bus: 

# En solicitud_controller.py
EventBus().publish(AppEvent.SOLICITUD_CREADA, solicitud)

La ventana principal (views/main_window.py) y otras vistas reaccionan dinámicamente suscribiéndose a estos eventos.

¿Por qué es una buena opción aquí?

  • Desacoplamiento Absoluto (Decoupling): Los controladores que procesan las solicitudes de tickets no saben nada de PyQt6. Esto permite reutilizar los controladores en una aplicación Web o API sin cambiar el código de lógica.
  • Actualizaciones Dinámicas: Varias pantallas se actualizan simultáneamente (Dashboard, Lista de Búsqueda) al ocurrir una acción en segundo plano.
# patterns/event_bus.py
class EventBus:
    # ... (Singleton) ...
    def subscribe(self, event: AppEvent, callback: Callable):
        if event not in self._subscribers:
            self._subscribers[event] = []
        self._subscribers[event].append(callback)

    def publish(self, event: AppEvent, data: Any = None):
        for callback in self._subscribers.get(event, []):
            callback(data)

Repository Arquitectura

Funciona como un mediador entre el dominio (los modelos de la aplicación) y la capa de acceso a datos, encapsulando las consultas SQL en clases dedicadas.

¿Dónde se implementa?

Clase Base: repositories/base_repository.py
Define los métodos CRUD genéricos usando clases abstractas (ABC).

Repositorios Concretos: en repositories/
SolicitudRepository, AlumnoRepository, UsuarioRepository y CatalogoRepository ejecutan las sentencias SQL correspondientes y mapean los resultados a objetos del modelo.

¿Por qué es una buena opción aquí?

  • Limpieza de código: La lógica de consultas SQL está aislada. Los controladores o modelos no contienen strings con código SQL.
  • Mapeo automático: Traduce automáticamente registros relacionales de la base de datos a instancias de clases orientadas a objetos (como Solicitud o Alumno).
  • Facilidad de migración: Si se decide cambiar SQLite por PostgreSQL o MySQL, solo se debe cambiar el código interno de los repositorios concretos sin afectar a la UI ni a la lógica del controlador.
# repositories/base_repository.py
from abc import ABC, abstractmethod

class BaseRepository(ABC, Generic[T]):
    @abstractmethod
    def get_by_id(self, id) -> Optional[T]: pass

    @abstractmethod
    def create(self, entity: T) -> T: pass

# Ejemplo de uso en Repositorio Concreto:
class SolicitudRepository(BaseRepository[Solicitud]):
    def get_by_id(self, id: int):
        cursor = self.db.cursor()
        cursor.execute("SELECT * FROM solicitudes...")
        return self._map_row_to_entity(cursor.fetchone())

Model-View-Controller (MVC) Arquitectura

El patrón estructural maestro de la aplicación. Divide el sistema en tres componentes interconectados para separar la representación de la información de la interacción del usuario.

¿Cómo está estructurado en el proyecto?

1. Modelos (models/): Representan las entidades del negocio (BaseModel, Alumno, Usuario, Solicitud). Contienen datos puros.

2. Vistas (views/): Desarrolladas en PyQt6. Son responsables del diseño visual, los botones, formularios y widgets (MainWindow, SolicitudPublicaView, etc.). No procesan datos.

3. Controladores (controllers/): Actúan como puentes. Reciben los datos y eventos de la vista, los validan y ejecutan las acciones llamando a los repositorios correspondientes (SolicitudController, AuthController).

¿Por qué es una buena opción aquí?

  • Código modular: Varios desarrolladores pueden trabajar simultáneamente (uno en el diseño visual de la UI y otro en la lógica del backend) sin pisarse el código.
  • Fácil de mantener: Si un cálculo de negocio cambia, solo se modifica en el controlador, la vista queda intacta.

Flujo de Datos MVC en el Sistema

1. VISTA: El administrador presiona "Registrar Solicitud" enviando un diccionario de datos.
↓
2. CONTROLADOR: Valida la CURP y las reglas del negocio, instancia el modelo Alumno y llama al Repositorio.
↓
3. MODELO & REPOSITORIO: Se ejecuta el comando SQL e inserta los datos de forma estructurada.

Template Method Comportamiento

Define el esqueleto de un algoritmo o comportamiento común en una superclase, delegando o permitiendo que las subclases hereden y utilicen este comportamiento sin duplicar código.

¿Dónde se implementa?

1. BaseView: views/base_view.py
Todas las vistas del sistema (LoginView, BusquedaView, etc.) heredan de BaseView. Esta clase define métodos comunes para alertar al usuario: show_error, show_info y show_warning.

2. BaseModel: models/base_model.py
Todos los modelos heredan de BaseModel, el cual implementa de forma genérica la transformación de datos a diccionario (to_dict) y la representación en texto (__repr__).

¿Por qué es una buena opción aquí?

  • Evita la duplicación de código (DRY - Don't Repeat Yourself): No es necesario escribir código para mostrar cuadros de diálogo de error de PyQt6 en cada pantalla. Solo se llama a self.show_error(...).
  • Consistencia: Todos los errores y mensajes se muestran de la misma forma en cualquier punto del sistema.
# views/base_view.py
from PyQt6.QtWidgets import QWidget, QMessageBox

class BaseView(QWidget):
    def show_error(self, message: str, title: str = "Error"):
        QMessageBox.critical(self, title, message)

    def show_info(self, message: str, title: str = "Información"):
        QMessageBox.information(self, title, message)

# Heredado en views/catalogos_view.py por ejemplo:
class CatalogosView(BaseView):
    def guardar(self):
        if error:
            self.show_error("No se pudo guardar el catálogo")

Conclusión y Calidad de Software

La combinación de estos patrones no es casualidad; es una decisión de ingeniería que eleva la calidad del software.

Métricas de Calidad de Software Beneficiadas

Mantenibilidad: Cambiar el diseño visual de un formulario PyQt6 no impactará en las reglas del negocio de los tickets (MVC).

Acoplamiento Bajo: Las vistas no conocen a la base de datos ni a los controladores de forma rígida gracias al EventBus y a la abstracción de Repository.

Extensibilidad: Agregar un nuevo flujo de trabajo o auditoría ante la creación de un ticket se realiza simplemente suscribiendo un nuevo método a AppEvent.SOLICITUD_CREADA sin alterar el código existente.
